# Deep plan: повторное заполнение анкеты с использованием прежних данных

## Проблема

При выборе пункта профиля «2. Заполнить заново» бот сразу вызывает `clearOnboardingFields`: обнуляет имя, год рождения, пол и био, удаляет сниппет и только после этого запускает onboarding. Пользователь вынужден вводить всю анкету заново и не может оставить отдельные прежние ответы.

Проблема воспроизведена через текущий webhook-entrypoint на изолированной временной D1: до команды существовали все поля и сниппет, после команды поля стали `NULL`, сниппет исчез, а состояние стало `onboarding:name`.

## Текущее поведение

1. `restartProfile` завершает активное редактирование профиля.
2. `clearOnboardingFields` необратимо очищает поля анкеты и сниппет в текущей базе.
3. Запускается обычный onboarding с шага имени.
4. Кнопок с прежними значениями нет, потому что прежние значения уже удалены.
5. Кнопка «Заново» на preview использует тот же очищающий helper.

## Целевое поведение

При повторном заполнении подтверждённой анкеты бот сохраняет исходные данные и последовательно задаёт те же вопросы. На каждом применимом шаге пользователь может нажать кнопку с прежним ответом или отправить новое значение:

- имя — кнопка содержит прежнее имя;
- год рождения — кнопка содержит прежний год;
- пол — прежнее значение доступно среди существующих кнопок выбора пола;
- био до 40 символов включительно — кнопка содержит прежнее био;
- био длиннее 40 символов — кнопка «Оставить прежнее»;
- если прежнего био нет, остаётся только возможность пропустить или ввести новое;
- сниппет — кнопка «Оставить прежнее», при нажатии сохраняются и полный текст, и язык прежнего сниппета.

Новые ответы продолжают сохраняться теми же запросами и проходят существующую валидацию. После preview и подтверждения профиль снова становится завершённым.

## Согласованные решения и открытые вопросы

Согласовано:

- прежние короткие значения показываются прямо в кнопках;
- граница длинного био — более 40 символов;
- для длинного био используется текст «Оставить прежнее»;
- для сниппета всегда используется «Оставить прежнее»;
- план сохраняется в этом файле на русском языке.

Открытых продуктовых вопросов нет.

## Ограничения и non-goals

- Не менять первичный onboarding для пользователей без прежней анкеты, кроме переиспользования общих keyboard/helper-функций.
- Не добавлять новые таблицы, колонки или D1-миграции.
- Не менять отдельные действия редактирования имени, года, пола, био и сниппета из профиля.
- Не менять карточки, ленту, мэтчинг, лайки, паузу профиля, transport local dev, webhook или deploy.
- Не превращать повторное заполнение в транзакционный draft: введённые ответы, как и сейчас, сохраняются по шагам; `/cancel` продолжает останавливать conversation с возможностью продолжить позже.
- Не писать автоматические тесты, поскольку это запрещено инструкциями проекта без отдельного запроса.
- Не трогать уже существующие несвязанные изменения в `.dev.vars.example`, `LOCAL_DEVELOPMENT.md`, `scripts/dev.ts`, `scripts/seed.ts`, `.temp/seed.sql` и `.temp/seed-profiles/`.

## Затронутые области

- `src/bot.ts` — запуск повторного onboarding без предварительного удаления анкеты, передача режима повторного заполнения и увеличение версии persistent conversation state после изменения replay-flow.
- `src/db/queries.ts` — узкий helper, который переводит профиль в `onboarding:refill:name` и сбрасывает только навигационное состояние, сохраняя поля и сниппет; существующий очищающий helper остаётся для настоящего сброса первичного onboarding.
- `src/flows/onboarding.ts` — снимок прежних данных, принудительный проход по всем полям в режиме повторного заполнения, обработка выбора прежнего био/сниппета и сохранение исходного baseline при повторном проходе из preview.
- `src/keyboards.ts` — динамические reply-клавиатуры с прежними значениями и действием «Оставить прежнее».
- `src/i18n/ru.ts`, `src/i18n/en.ts` — локализованная подпись действия «Оставить прежнее» / `Keep previous`.

## UX-состояния

### Первичное заполнение

Поведение не меняется: прежних данных нет, дополнительные кнопки не показываются.

### Повторное заполнение

Каждый шаг показывает применимую кнопку со старым ответом. Нажатие кнопки эквивалентно повторному выбору старого значения; ручной ввод заменяет его.

### Био

- Нет прежнего био: `Пропустить` и ручной ввод.
- Прежнее био длиной 1–40 символов: кнопка с полным прежним текстом плюс `Пропустить`.
- Прежнее био длиннее 40 символов: `Оставить прежнее` плюс `Пропустить`.

### Сниппет

- Есть прежний сниппет: `Оставить прежнее` или отправка нового кода.
- Нет прежнего сниппета: текущий обязательный ввод кода без дополнительной кнопки.

### Preview и «Заново»

В режиме повторного заполнения исходный snapshot сохраняется на время активной conversation. Если пользователь на preview нажимает «Заново», flow возвращается к имени без удаления исходного baseline, поэтому прежние значения снова доступны в кнопках. Для обычного первичного onboarding текущая очистка при «Заново» сохраняется.

## Поток данных и состояния

1. `restartProfile` загружает завершённого пользователя и переводит его в `onboarding:refill:name` без очистки полей и сниппета. Префикс `onboarding:refill:*` сохраняет режим при `/cancel` → `/start` без новой колонки или миграции.
2. Conversation запускается с явным режимом повторного заполнения.
3. В начале conversation через `conversation.external` один раз загружаются пользователь и единственный сниппет; эти JSON-сериализуемые данные становятся baseline, который grammY сохраняет вместе с replay-состоянием.
4. Каждый `ask*` получает соответствующее прежнее значение и строит reply keyboard.
5. Выбор буквального старого значения проходит через существующую валидацию и сохраняется обычным способом.
6. Выбор «Оставить прежнее» для длинного био или сниппета распознаётся только на соответствующем шаге и записывает исходное полное значение, а не текст кнопки.
7. Новый ответ заменяет текущее значение теми же `patchUser`/`upsertSnippet`, что и сейчас.
8. После подтверждения `completeProfile` возвращает `state` в `NULL`.

## Simplification gate

- Существующие `askName`, `askYear`, `askGender`, `askBio`, `askSnippetText`, `saveSnippet` и validation helpers переиспользуются; отдельный новый onboarding не создаётся.
- Существующий `clearOnboardingFields` не переопределяется как «сохранить старое», потому что он нужен для настоящей очистки первичного onboarding и preview reset.
- Snapshot хранится в уже существующем conversation state; отдельное draft-хранилище и миграция не нужны.
- Меняется минимальный набор runtime-файлов: запуск flow, query helper, onboarding, keyboards и две локали.

## Риски и крайние случаи

- Старое био и сниппет нельзя подменить текстом generic-кнопки: обработчик должен сохранять baseline, а не строку «Оставить прежнее».
- Значение пола `0` нельзя проверять через truthiness; только через `null`/`undefined`.
- Пустое прежнее био (`NULL`) не должно создавать keep-кнопку.
- Snapshot должен включать язык сниппета, иначе повторное использование кода может изменить подсветку.
- grammY conversation arguments не имеют статической проверки типов; refill-режим и snapshot нужно типизировать в builder signature и передавать только JSON-сериализуемые значения.
- Изменение структуры conversation требует новой storage version; старые активные conversation будут безопасно отброшены и продолжатся с шага, сохранённого в `users.state`.
- При `/cancel` после ввода новых значений остаётся существующая пошаговая модель сохранения; откат всей анкеты не входит в scope.
- Реальное отображение длинных reply-кнопок в Telegram останется UI-риском до ручной проверки.
